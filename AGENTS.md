## Communication and explanation

Optimize outputs for human understanding, inspection, and verification.

### Writing style

For technical explanations, use approximately "80% ASD-STE100" style:

- Use short, direct sentences.
- Prefer concrete words over abstract or ornamental language.
- Use the same term for the same concept throughout the explanation.
- Prefer active voice when it makes the actor clear.
- Put one main idea or instruction in each sentence.
- State conditions before actions when useful.
- Define unfamiliar abbreviations and domain-specific terms.
- Avoid filler, rhetorical introductions, and unnecessary restatement.
- Do not make prose artificially rigid when normal technical English is clearer.

Prefer:

> The server validates the token before it reads the request body.

over:

> Prior to proceeding with processing of the incoming request body,
> validation of the supplied token is performed by the server.

### Choose the best representation

Do not assume prose is the best output format.

Choose the representation that makes the underlying structure easiest to
understand:

- Use concise prose for simple facts, conclusions, and instructions.
- Use tables for comparisons or repeated structured data.
- Use diagrams for architecture, relationships, flows, state transitions,
  dependencies, and causal chains.
- Use timelines for sequences of events.
- Use interactive HTML or small tools when the user would benefit from
  exploring parameters, states, alternatives, or large structured outputs.
- Use animation or video only when change over time is central to understanding
  and the required tools are available.

Prefer one clear visual representation over several paragraphs that describe
the same structure.

### Build disposable explanation tools when useful

If a concept is difficult to understand in static prose, consider creating a
small, task-specific artifact rather than writing a longer explanation.

Examples:

- an interactive dependency graph for a codebase
- a request-flow diagram for a distributed system
- a small HTML simulator for an algorithm
- an interactive before/after view for a UI change
- a visual state machine for application behavior
- a generated report that lets the user expand details on demand

These artifacts do not need to become production software. They can exist only
to help the user understand or verify the current task.

Do not create an artifact merely because it is possible. Create one when it
reduces the user's cognitive load.

### Progressive disclosure

Lead with the smallest useful mental model.

Then provide deeper detail only where it helps.

A good explanation often follows this order:

1. What happened or what the system does.
2. The important components and their relationships.
3. The relevant implementation details.
4. Edge cases, assumptions, and failure modes.
5. Raw details or source material when needed.

Do not force the user to read implementation detail before they understand the
overall structure.

### Make generated work easy to inspect

When producing or modifying substantial code, help the user supervise the
result.

Explain:

- what changed
- where it changed
- why the change was necessary
- important assumptions
- important tradeoffs
- what was verified
- what remains uncertain

For large changes, prefer a diagram, dependency map, concise change summary, or
other structured representation over a file-by-file narration.

### Distinguish implementation from explanation

The implementation can be complex while the explanation remains simple.

Do not mirror the complexity of the code in the explanation.

Translate implementation detail into the smallest accurate mental model that
lets the user reason about the system.

### Prefer evidence over confidence

When claiming that something works, point to the evidence:

- tests
- compiler/type-check results
- runtime output
- measurements
- inspected code paths
- relevant source documentation

Clearly distinguish:

- verified facts
- reasonable inferences
- assumptions
- unresolved questions

### Avoid unnecessary output

Do not produce a long explanation simply because substantial work was done.

The amount of explanation should be proportional to what the user needs to
understand and verify the result, not to the amount of computation or code
generated by the agent.

## Explain systems, not diffs

When a change touches multiple files, do not default to describing every edit
file by file.

First explain the resulting system.

For example:

    User request
         |
         v
    API handler
         |
         v
    Validation
         |
         v
    Domain service
         |
         +------> Database
         |
         +------> External API

Then identify which parts changed.

The user should be able to answer these questions after reading the summary:

- What is the system doing now?
- What changed from before?
- Why does the new design work?
- Where are the important boundaries?
- What could still fail?
- How was the result verified?

If prose cannot answer these efficiently, create a diagram or another
appropriate explanatory artifact.

## Engineering

- When making technical decisions, give little weight to development cost. Prefer quality, simplicity, robustness, and long-term maintainability.
- For one-off or infrequent operational work, take the simplest direct path. Build wrappers, automation, or custom tooling only when the direct path hits a concrete blocker or a repeated need.
- Do not edit `CHANGELOG.md` or other generated files by hand.
- When testing a UI end to end, be picky about what you see. If something looks off, fix it, even if it is unrelated to the task. Treat lint errors, test failures, and flaky tests the same way. If the fix is large, report it instead of expanding the task.
- Before a refactor, check that tests cover the behavior it touches. If coverage is missing, add tests first, at the public interface or E2E level, and confirm they pass before changing code.
- Before reporting a non-trivial change as done, have a separate subagent review it adversarially against the original request. Report what the review found and what you fixed.
- Prefer E2E tests as the primary way to verify features.
- E2E tests should exercise realistic user or system workflows and, when practical, produce a repeatable artifact that can be independently inspected or reproduced.
- Do not write unit tests merely to mirror implementation details or increase test count.
- Use unit, property-based, or isolated tests when the logic has important edge cases, invariants, combinatorial behavior, or failure modes that are impractical to verify through E2E tests alone.
- Before writing isolated tests, explicitly identify the important ways the component can fail, then write tests against those failure modes.
- Avoid writing tests after implementation solely to justify the existing code. Tests should validate intended behavior, not encode accidental implementation details.
- Apply the `unslop` skill (`~/.agents/skills/unslop/SKILL.md`) to all drafted prose before it leaves the workspace: PR bodies and review replies, commit messages, comments, docs. No em dashes.
